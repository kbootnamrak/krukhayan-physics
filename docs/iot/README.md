# ระบบติดตามอุณหภูมิและความชื้น (ESP32 + DHT11)

เอกสารออกแบบระบบ — อ่านคู่กับโค้ดใน `firmware/esp32-dht11/`, `src/app/api/iot/`,
`src/app/dashboard/iot/` และ `supabase/migrations/`

---

## 1. ระบบนี้ทำอะไร

บอร์ด ESP32 พร้อมเซนเซอร์ DHT11 วัดอุณหภูมิและความชื้นตามรอบเวลา ส่งขึ้นเว็บผ่าน Wi-Fi
เว็บเก็บข้อมูลลง Supabase แสดงเป็นกราฟย้อนหลัง และส่งข้อความแจ้งเตือนทาง LINE
เมื่อค่าที่วัดได้หลุดจากเกณฑ์ที่ครูตั้งไว้ หรือเมื่ออุปกรณ์ขาดการติดต่อ

ออกแบบให้ต่อยอดจากเว็บ krukhayan-physics ที่มีอยู่แล้ว ใช้ Supabase และ Vercel
โปรเจกต์เดิม ไม่ต้องตั้งเซิร์ฟเวอร์ใหม่และไม่มีค่าใช้จ่ายรายเดือนเพิ่ม

---

### ทำไมตรรกะการแจ้งเตือนอยู่ฝั่งเซิร์ฟเวอร์ ไม่ใช่ในบอร์ด

1. **แก้เกณฑ์ได้ทันที** — ครูเปลี่ยนค่าในหน้าเว็บ ไม่ต้องเดินไปแฟลชบอร์ดใหม่ทุกครั้ง
2. **บอร์ดที่ตายแล้วเตือนตัวเองไม่ได้** — ไฟดับ บอร์ดค้าง หรือ Wi-Fi ล่ม บอร์ดจะเงียบไปเฉย ๆ
   ซึ่งเป็นความผิดปกติที่อันตรายที่สุด ต้องมีฝั่งเซิร์ฟเวอร์คอยจับว่า "ไม่มีข้อมูลเข้ามา"
3. **บอร์ดเก็บความลับไม่ได้** — token ของ LINE ถ้าฝังในบอร์ด ใครถอดบอร์ดไปก็อ่านได้

บอร์ดจึงมีหน้าที่เดียว: วัดแล้วส่ง

## 3. อุปกรณ์ที่ต้องใช้ (ต่อหนึ่งจุดวัด)

| รายการ | รายละเอียด | ราคาโดยประมาณ |
|---|---|---|
| บอร์ด ESP32 | **ESP32-WROOM-32E** 4MB (ดูหัวข้อ 3.1) | 200–300 บาท |
| สาย USB **แบบส่งข้อมูลได้** | ดูว่าบอร์ดเป็น Micro-USB หรือ Type-C | 50–80 บาท |
| โมดูล DHT11 | แบบ 3 ขา (มีตัวต้านทาน pull-up มาให้แล้ว) | 40–60 บาท |
| สายจัมเปอร์เมีย–เมีย | 3 เส้น | 20–40 บาท |
| อะแดปเตอร์ USB 5V | **1A ขึ้นไป** (ดูหัวข้อ 3.3) | 80–120 บาท |
| กล่องอะคริลิก | เจาะรูให้เซนเซอร์สัมผัสอากาศ | 80–150 บาท |
| **รวม** | | **ประมาณ 470–750 บาท** |

บอร์ดหลายร้านขายพร้อมสาย USB ในกล่องเดียว (เช่น ชุด WROOM-32E + สาย Type-C ราว 295 บาท)
ซึ่งราคาพอ ๆ กับแยกซื้อ แต่ไม่เสี่ยงได้สายชาร์จที่ส่งข้อมูลไม่ได้มา

**ไม่ต้องซื้อ** เบรดบอร์ด · ตัวต้านทาน · หัวแร้ง — ถ้าใช้โมดูล DHT11 แบบ 3 ขาและบอร์ดที่บัดกรีขามาแล้ว
งานนี้ไม่ต้องบัดกรีเลยสักจุด

ค่าบริการฝั่งคลาวด์: Supabase free tier และ Vercel Hobby รองรับปริมาณข้อมูลระดับนี้ได้สบาย
(ดูหัวข้อ 12) — ไม่มีค่าใช้จ่ายรายเดือน

### 3.1 เลือกรุ่นบอร์ดให้ถูก — 32E หรือ 32UE

ชื่อรุ่นต่างกันตัวอักษรเดียวแต่ใช้แทนกันไม่ได้

| รุ่น | เสาอากาศ | เหมาะกับ |
|---|---|---|
| **ESP32-WROOM-32E** | ลายวงจรบนบอร์ด มีมาในตัว | ติดนอกตู้ บนผนัง หรือในกล่องพลาสติก/อะคริลิก |
| ESP32-WROOM-32UE | หัวต่อ U.FL — **ต้องซื้อเสาอากาศเพิ่ม** | ต้องติดในตู้เหล็ก แล้วเดินสายเสาออกมานอกตู้ |

ตัว **U** ย่อมาจาก external antenna ถ้าซื้อ 32UE มาแล้วไม่ต่อเสา จะจับ Wi-Fi แทบไม่ติดเลย

> **ห้องเซิร์ฟเวอร์มักมีตู้แร็คเหล็ก และโลหะบังสัญญาณ Wi-Fi**
> ถ้าจำเป็นต้องวางบอร์ดไว้ในตู้แร็คปิด ให้ใช้ 32UE พร้อมเสาอากาศภายนอก แล้วเดินสายเสาออกมานอกตู้
> ถ้าติดนอกตู้หรือบนผนังได้ ใช้ 32E ตามปกติ

### 3.2 ถามร้าน 2 ข้อก่อนกดซื้อ

1. **บัดกรีขาเสียบ (pin header) มาให้แล้วหรือยัง** — บอร์ดทรงเล็กบางร้านส่งมาเป็นรูเปล่าพร้อมขาแยกในถุง
   ถ้าเป็นแบบนั้นต้องใช้หัวแร้งบัดกรีเอง
2. **ใช้ชิป USB ตัวไหน (CH340 หรือ CP2102)** — ไว้ลงไดรเวอร์ให้ถูก (ดูหัวข้อ 11.4)

### 3.3 อะแดปเตอร์ต้องจ่ายได้อย่างน้อย 1A

ESP32 กินไฟปกติราว 80 mA แต่**พุ่งถึง 500 mA ในจังหวะที่ส่งสัญญาณ Wi-Fi**

ถ้าอะแดปเตอร์จ่ายไม่ทันหรือใช้สายยาวเส้นเล็ก ไฟจะตกชั่วขณะแล้วบอร์ดรีสตาร์ทตัวเอง
ขึ้นข้อความ `Brownout detector was triggered` ใน Serial Monitor — เป็นอาการที่หาสาเหตุยาก
เพราะดูเหมือนบอร์ดเสีย ทั้งที่จริงเป็นเรื่องไฟเลี้ยง ใช้อะแดปเตอร์ 1A ขึ้นไป (2A ยิ่งดี) แล้วจะไม่เจอ

## 4. การต่อวงจร

โมดูล DHT11 แบบ 3 ขา ต่อตรงได้เลย ไม่ต้องใช้ตัวต้านทานเพิ่ม

| ขาโมดูล DHT11 | ต่อเข้ากับ ESP32 |
|---|---|
| VCC (+) | 3V3 |
| DATA (OUT / S) | GPIO 4 |
| GND (−) | GND |

```
   ESP32                DHT11 module
  ┌────────┐            ┌─────────┐
  │   3V3  ├────────────┤ +  (VCC)│
  │ GPIO4  ├────────────┤ S (DATA)│
  │   GND  ├────────────┤ −  (GND)│
  └────────┘            └─────────┘
```

> ### ⚠️ ต่อ VCC เข้าขา 3V3 เท่านั้น — ห้ามต่อ 5V เด็ดขาด
>
> ขา I/O ของ ESP32 ทำงานที่ 3.3V และ**ทนสัญญาณ 5V ไม่ได้** ถ้าเลี้ยง DHT11 ด้วย 5V
> ขา DATA จะส่งสัญญาณ 5V กลับเข้า GPIO 4 ซึ่งทำให้ขานั้นพังถาวร
>
> บทความ DHT11 ตามอินเทอร์เน็ตส่วนใหญ่เขียนจากฝั่ง Arduino Uno ที่ใช้ 5V ได้ —
> **ใช้ตามไม่ได้กับ ESP32**

**ถ้าใช้ DHT11 แบบ 4 ขา (ตัวเปล่า)** ต้องต่อตัวต้านทาน 10 kΩ คร่อมระหว่างขา VCC กับขา DATA
และขาที่ 3 ปล่อยลอยไว้

**ข้อควรระวังในการติดตั้ง**
- อย่าติดเซนเซอร์ไว้ในกล่องปิดสนิทหรือชิดตัวบอร์ด ความร้อนจากตัว ESP32 เองจะทำให้ค่าสูงกว่าจริง 1–3 °C
  ให้เจาะรูระบายอากาศ หรือใช้สายยาวแยกเซนเซอร์ออกมานอกกล่อง
- อย่าติดตรงทางลมแอร์เป่าโดยตรง หรือโดนแดดส่อง จะวัดได้ค่าที่ไม่แทนสภาพห้องจริง
- ติดสูงจากพื้นประมาณ 1.2–1.5 เมตร ห่างผนัง 30 ซม.

## 5. ข้อจำกัดของ DHT11 (สำคัญ — อ่านก่อนตัดสินใจ)

| หัวข้อ | DHT11 | DHT22 | SHT31 |
|---|---|---|---|
| ช่วงอุณหภูมิ | 0 – 50 °C | −40 – 80 °C | −40 – 125 °C |
| ความคลาดเคลื่อนอุณหภูมิ | ±2 °C | ±0.5 °C | ±0.3 °C |
| ความละเอียดอุณหภูมิ | 1 °C | 0.1 °C | 0.01 °C |
| ช่วงความชื้น | 20 – 90 %RH | 0 – 100 %RH | 0 – 100 %RH |
| ความคลาดเคลื่อนความชื้น | ±5 %RH | ±2 %RH | ±2 %RH |
| อ่านได้ถี่สุด | 1 ครั้ง / 1–2 วินาที | 1 ครั้ง / 2 วินาที | เร็วกว่ามาก |
| ราคา | ~50 บาท | ~150 บาท | ~250 บาท |

DHT11 **อ่านอุณหภูมิเป็นจำนวนเต็ม** กราฟจึงเป็นขั้นบันได ไม่ใช่เส้นโค้งเรียบ — เป็นเรื่องปกติ ไม่ใช่ความผิดพลาด

**เลือก DHT11 ได้ถ้า** ต้องการดูแนวโน้มห้องเรียน ห้องพักครู คลังเก็บของทั่วไป
**ควรเปลี่ยนเป็น DHT22 หรือ SHT31 ถ้า**
- ต้องวัดต่ำกว่า 0 °C (ตู้เย็นเก็บยา ห้องเย็น) — DHT11 วัดไม่ได้เลย
- ต้องการความแม่นระดับ ±0.5 °C เพื่อใช้อ้างอิงทางการ
- งานที่มีข้อกำหนดทางกฎหมายรองรับ เช่น ห้องยาตามมาตรฐานเภสัชกรรม

โค้ดรองรับการเปลี่ยนเซนเซอร์อยู่แล้ว แก้บรรทัดเดียวใน `config.h`:
```c
#define DHT_TYPE DHT22
```
ฐานข้อมูลและฝั่งเว็บไม่ต้องแก้อะไรเลย (ช่วงค่าที่ยอมรับตั้งไว้กว้างกว่า DHT11 อยู่แล้ว
ดู `SENSOR_RANGE` ใน `src/lib/iot/types.ts`)

## 6. โครงสร้างฐานข้อมูล

ทุกตารางขึ้นต้นด้วย `iot_` เพื่อไม่ชนกับตารางระบบคะแนนเดิม

| ตาราง | เก็บอะไร |
|---|---|
| `iot_devices` | อุปกรณ์แต่ละตัว: ชื่อ ตำแหน่ง ค่า hash ของ device key เวลาที่ได้ยินครั้งล่าสุด |
| `iot_readings` | ค่าที่วัดได้ทุกครั้ง (unique ที่ `device_id + recorded_at`) |
| `iot_alert_rules` | เกณฑ์ต่ออุปกรณ์ต่อค่าที่วัด: ต่ำสุด สูงสุด ค่าหน่วง จำนวนครั้งติดกัน ระยะพัก |
| `iot_alert_states` | สถานะปัจจุบันของแต่ละเกณฑ์ (ใช้ทำ hysteresis / cooldown) |
| `iot_alerts` | ประวัติการแจ้งเตือน พร้อมผลว่าส่ง LINE สำเร็จหรือไม่ |
| `iot_line_recipients` | ผู้รับแจ้งเตือน (`device_id` เป็น null = รับทุกอุปกรณ์) |
| `iot_device_latest` | วิวสรุปค่าล่าสุด + สถานะออนไลน์ของแต่ละอุปกรณ์ |

### สิทธิ์การเข้าถึง (Row Level Security)

| ตาราง | นักเรียน / ผู้ล็อกอินทั่วไป | ครู | อุปกรณ์ |
|---|---|---|---|
| `iot_devices`, `iot_readings` | อ่านได้ | อ่าน/แก้ได้ | เขียนผ่าน API เท่านั้น |
| `iot_alert_rules`, `iot_alerts` | อ่านได้ | อ่าน/แก้ได้ | – |
| `iot_alert_states` | เข้าไม่ถึง | อ่าน/แก้ได้ | – |
| `iot_line_recipients` | เข้าไม่ถึง | อ่าน/แก้ได้ | – |

ตาราง `iot_line_recipients` เก็บ LINE userId ซึ่งระบุตัวบุคคลได้ จึงปิดไม่ให้ผู้ใช้ทั่วไปอ่าน

อุปกรณ์ไม่มีบัญชีใน Supabase และไม่ถือ anon key — เขียนข้อมูลผ่าน `/api/iot/ingest`
ซึ่งใช้ service role ฝั่งเซิร์ฟเวอร์เท่านั้น

### จุดออกแบบที่ตั้งใจ

- **`unique (device_id, recorded_at)`** — อุปกรณ์ส่งซ้ำเพราะ retry หรือส่งข้อมูลค้างในบัฟเฟอร์
  ซ้ำกับที่ส่งไปแล้ว จะถูกข้ามโดยอัตโนมัติ ไม่เกิดข้อมูลซ้อน (การส่งข้อมูลเป็น idempotent)
- **เก็บเฉพาะ hash ของ device key** — ฐานข้อมูลรั่วก็เอาคีย์ไปใช้ต่อไม่ได้
- **`unique nulls not distinct` ในตารางผู้รับ** — แถวที่ `device_id` เป็น null (รับทุกอุปกรณ์)
  ต้องชนกันเองได้ ไม่งั้น webhook ของ LINE จะสร้างแถวซ้ำทุกครั้งที่ผู้ใช้ทักบอท

## 7. ลำดับการทำงานเมื่อมีข้อมูลเข้ามา

```
ESP32 ──POST──▶ /api/iot/ingest
                 │
                 ├─ ไม่มี x-device-key ────────────────────▶ 401
                 ├─ hash ไม่ตรงกับอุปกรณ์ไหนเลย ────────────▶ 401
                 ├─ อุปกรณ์ถูกปิดใช้งาน ───────────────────▶ 403
                 ├─ ค่าเกินพิสัยที่เซนเซอร์วัดได้ ──────────▶ ตัดทิ้งเฉพาะค่านั้น
                 ├─ เวลาที่แนบมาเพี้ยน (นาฬิกาบอร์ดผิด) ────▶ ใช้เวลาเซิร์ฟเวอร์แทน
                 │
                 ├─ บันทึกลง iot_readings (ซ้ำก็ข้าม)
                 ├─ อัปเดต last_seen_at
                 │
                 └─ สำหรับแต่ละเกณฑ์ที่เปิดอยู่:
                      evaluateRule(เกณฑ์, สถานะเดิม, ค่าล่าสุด)
                        │
                        ├─ ไม่มีอะไรเปลี่ยน ──────▶ อัปเดตสถานะ จบ
                        └─ ต้องเตือน ────────────▶ บันทึก iot_alerts
                                                   └─ push LINE ให้ผู้รับทุกคน
```

ตอบกลับ `sample_interval_s` และ `server_time` ทุกครั้ง เพื่อให้บอร์ดปรับจังหวะการส่ง
และเทียบนาฬิกาได้โดยไม่ต้องแฟลชใหม่

## 8. API

### `POST /api/iot/ingest`

```
Headers: x-device-key: kkp_xxxxxxxxxxxx
         Content-Type: application/json
```

ส่งค่าเดียว:
```json
{ "temperature_c": 27.4, "humidity_pct": 61, "rssi": -63 }
```

ส่งเป็นชุด (ข้อมูลที่ค้างในบัฟเฟอร์ตอนเน็ตหลุด สูงสุด 60 รายการต่อครั้ง):
```json
{ "readings": [
  { "recorded_at": "2026-09-16T03:00:00Z", "temperature_c": 27.4, "humidity_pct": 61 },
  { "recorded_at": "2026-09-16T03:01:00Z", "temperature_c": 27.5, "humidity_pct": 60 }
] }
```

ตอบกลับ:
```json
{ "ok": true, "accepted": 2, "skipped": 0,
  "sample_interval_s": 60, "server_time": "2026-09-16T03:01:04.812Z" }
```

| สถานะ | ความหมาย |
|---|---|
| 200 | รับข้อมูลแล้ว |
| 400 | JSON ไม่ถูกต้อง หรือจำนวนรายการเกิน 60 |
| 401 | ไม่มี device key หรือคีย์ไม่ถูกต้อง |
| 403 | อุปกรณ์ถูกปิดใช้งาน |
| 422 | ไม่มีค่าไหนอยู่ในพิสัยที่เซนเซอร์วัดได้เลย |

### `POST /api/iot/devices` (ต้องล็อกอินเป็นครู)
สร้างอุปกรณ์ใหม่ พร้อมสร้างเกณฑ์เริ่มต้น (อุณหภูมิ 18–28 °C, ความชื้น 30–70 %RH)
คืน device key กลับมา **ครั้งเดียว**

### `POST /api/iot/devices/[id]/key` (ต้องล็อกอินเป็นครู)
ออกคีย์ใหม่ คีย์เดิมใช้ไม่ได้ทันที

ต้องมี `Authorization: Bearer <CRON_SECRET>` — ตรวจว่ามีอุปกรณ์ตัวไหนเงียบหายไป

### `POST /api/iot/line/webhook`
LINE เรียกเข้ามาเอง ตรวจลายเซ็นด้วย `LINE_CHANNEL_SECRET`

## 9. ตรรกะการแจ้งเตือน

โจทย์ของระบบเตือนไม่ใช่ "เตือนให้ครบ" แต่คือ **"เตือนเฉพาะตอนที่ควรเตือน"**
ถ้าเตือนบ่อยเกินไปคนจะเลิกอ่าน แล้วก็จะพลาดครั้งที่สำคัญจริง ๆ ระบบนี้จึงมีกลไกกันเสียง 4 ชั้น

### 9.1 ต้องผิดติดกันหลายครั้ง (`consecutive_required` ค่าเริ่มต้น 2)

DHT11 อ่านพลาดเป็นครั้งคราว ค่าที่กระโดดครั้งเดียวจึงยังไม่เตือน
ต้องผิดเกณฑ์ติดกันตามจำนวนที่ตั้งไว้ก่อน — ที่รอบ 60 วินาที หมายถึงหน่วงราว 1 นาที

### 9.2 ค่าหน่วง (`hysteresis` ค่าเริ่มต้น 0.5 °C)

เกณฑ์สูงสุด 30 °C, ค่าหน่วง 0.5 →
- เตือนเมื่อค่าเกิน **30.0**
- ถือว่ากลับสู่ปกติเมื่อค่าลดลงถึง **29.5**

ถ้าไม่มีค่าหน่วง ค่าที่แกว่งอยู่รอบ ๆ 30 พอดี (29.9 / 30.1 / 29.9 / 30.1) จะยิงข้อความ
"เกินเกณฑ์" สลับ "กลับสู่ปกติ" ไปมาไม่หยุด

### 9.3 ระยะพักก่อนเตือนซ้ำ (`cooldown_minutes` ค่าเริ่มต้น 15)

ถ้าค่ายังผิดเกณฑ์ค้างอยู่ ระบบจะเตือนซ้ำทุก 15 นาที — ไม่ใช่ทุกนาที และไม่ใช่เตือนครั้งเดียวแล้วเงียบ
เตือนซ้ำเพราะปัญหาที่ยังไม่ถูกแก้ต้องไม่หายไปจากสายตา

### 9.4 แจ้งเมื่ออุปกรณ์ขาดการติดต่อ

`offline_after_s` (ค่าเริ่มต้น 300 วินาที) — ไม่ได้ยินจากอุปกรณ์เกินเท่านี้ถือว่าออฟไลน์
ตรวจโดย cron เพราะอุปกรณ์ที่ตายแล้วไม่มีทางยิงคำขอเข้ามาเองได้

### ตัวอย่างลำดับเหตุการณ์ (เกณฑ์สูงสุด 30 °C, ค่าหน่วง 0.5, ผิดติดกัน 2, พัก 15 นาที)

| เวลา | ค่า | สิ่งที่เกิดขึ้น |
|---|---|---|
| 10:00 | 29.8 | ปกติ |
| 10:01 | 30.4 | ผิดครั้งที่ 1 — ยังไม่เตือน |
| 10:02 | 30.6 | ผิดครั้งที่ 2 — **ส่ง LINE "อุณหภูมิสูงเกินกำหนด 30.6 °C"** |
| 10:03–10:16 | 31.x | ยังผิดอยู่ แต่อยู่ในระยะพัก — เงียบ |
| 10:17 | 31.2 | พ้นระยะพัก — **ส่ง LINE ซ้ำ** |
| 10:20 | 29.8 | ยังไม่ต่ำกว่า 29.5 → ยังถือว่าผิดอยู่ (ผลของค่าหน่วง) |
| 10:21 | 29.3 | ต่ำกว่า 29.5 — **ส่ง LINE "กลับสู่ปกติแล้ว"** |

ตรรกะทั้งหมดอยู่ใน `src/lib/iot/alerts.ts` เขียนเป็นฟังก์ชันบริสุทธิ์
(รับสถานะเข้า คืนสถานะออก ไม่แตะฐานข้อมูล ไม่ส่ง LINE) จึงทดสอบได้โดยไม่ต้องมีอุปกรณ์จริง

## 10. ตั้งค่าแจ้งเตือน LINE

> **LINE Notify ปิดให้บริการไปแล้วเมื่อ 31 มีนาคม 2568** บทความเก่า ๆ ที่สอนใช้
> `notify-api.line.me` ใช้ไม่ได้อีกต่อไป ระบบนี้ใช้ **LINE Messaging API** แทน

### ขั้นตอน

1. เข้า [LINE Developers Console](https://developers.line.biz/console/) ล็อกอินด้วยบัญชี LINE
2. สร้าง **Provider** (เช่น "โรงเรียน...") แล้วสร้าง **Channel** ชนิด **Messaging API**
3. ในแท็บ **Messaging API**
   - กด **Issue** เพื่อออก **Channel access token (long-lived)** → เก็บไว้เป็น `LINE_CHANNEL_ACCESS_TOKEN`
   - ตั้ง **Webhook URL** เป็น `https://<โดเมนของเว็บ>/api/iot/line/webhook` แล้วเปิด **Use webhook**
   - ปิด **Auto-reply messages** และ **Greeting messages** (ไม่งั้นบอทจะตอบข้อความอัตโนมัติกวน)
4. ในแท็บ **Basic settings** คัดลอก **Channel secret** → เก็บไว้เป็น `LINE_CHANNEL_SECRET`
5. ใส่ค่าทั้งสองใน Vercel → Project Settings → Environment Variables แล้ว redeploy
6. ให้ครูทุกคนที่ต้องการรับแจ้งเตือน **สแกน QR ของบอทเพื่อแอดเป็นเพื่อน แล้วทักไปหนึ่งข้อความ**
   ระบบจะเก็บ userId ให้อัตโนมัติ และบอทจะตอบกลับว่าลงทะเบียนแล้ว
7. ตรวจรายชื่อผู้รับได้ที่หน้า `/dashboard/iot/<อุปกรณ์>` แท็บ "ผู้รับแจ้งเตือน"

### ส่งเข้ากลุ่ม LINE

เชิญบอทเข้ากลุ่ม ระบบจะเก็บ `groupId` จาก event `join` ให้เอง ข้อความจะเข้ากลุ่มแทนที่จะเข้าแชทส่วนตัว

### โควตา

บัญชี Messaging API แบบฟรีส่งข้อความเชิงรุก (push) ได้จำกัดต่อเดือน
ด้วยกลไกกันเสียงในหัวข้อ 9 การใช้งานปกติจะอยู่ในระดับหลักสิบข้อความต่อเดือน ไม่ใกล้เพดาน
แต่ถ้าตั้งเกณฑ์แคบเกินไปจนเตือนทั้งวัน โควตาจะหมดได้ — ตรวจโควตาปัจจุบันได้ใน LINE Developers Console

`vercel.json` ตั้งไว้ให้เรียกวันละครั้ง (05:00 น. เวลาไทย) เพราะ**แพลน Hobby ของ Vercel
ไม่ยอมให้ deploy เลยถ้าตั้ง cron ถี่กว่าวันละครั้ง** — ไม่ใช่แค่ทำงานไม่ครบตามตาราง
แต่ deploy ไม่ผ่านตั้งแต่ต้น

วันละครั้งช้าเกินไปสำหรับการแจ้งเตือนจริง จึงควรทำอย่างใดอย่างหนึ่งเพิ่ม

  ตั้งให้ยิง `GET https://<โดเมน>/api/iot/cron/offline-check` พร้อม header
  `Authorization: Bearer <CRON_SECRET>` ทุก 5–15 นาที ฟรีและไม่ต้องอัปเกรดแพลน
- **หรืออัปเกรดเป็นแพลน Pro** แล้วเปลี่ยน `schedule` ใน `vercel.json` เป็น `*/15 * * * *`

สถานะ "ออฟไลน์" ในหน้าเว็บคำนวณสดจากเวลาที่ได้ยินครั้งล่าสุด จึงถูกต้องเสมอ
ไม่ขึ้นกับ cron — cron มีหน้าที่ยิงข้อความ LINE เท่านั้น

### 11.4 บอร์ด ESP32

**ขั้นที่ 1 — ลงไดรเวอร์ USB ก่อน (ทำก่อนเสียบบอร์ด)**

บอร์ด ESP32 คุยกับคอมผ่านชิปแปลง USB ซึ่งต้องมีไดรเวอร์ก่อน

| ชิปบนบอร์ด | Windows | macOS | Linux |
|---|---|---|---|
| **CH340 / CH341** | ต้องลง — ค้นหา `CH341SER driver` จากเว็บผู้ผลิต WCH (wch-ic.com) | เวอร์ชันใหม่มีมาให้แล้ว ถ้าไม่เห็นพอร์ตค่อยลง CH34x driver | มีในตัว |
| **CP2102** | ต้องลง — ค้นหา `CP210x VCP driver` จากเว็บ Silicon Labs | มักมีมาให้แล้ว | มีในตัว |

**วิธีตรวจว่าสำเร็จ:** เสียบบอร์ดเข้าคอม → เปิด Arduino IDE → เมนู **Tools › Port**
ต้องเห็นพอร์ตใหม่โผล่ขึ้นมา (Windows: `COM3`, `COM4`… / macOS: `/dev/cu.wchusbserial…`)
ถ้าไม่เห็น แปลว่าไดรเวอร์ยังไม่ติด หรือสาย USB ที่ใช้เป็นสายชาร์จที่ส่งข้อมูลไม่ได้

**ขั้นที่ 2 — เตรียม Arduino IDE**

1. ติดตั้ง Arduino IDE แล้วเพิ่ม Board Manager URL ของ Espressif (`esp32 by Espressif Systems`)
2. Library Manager ติดตั้ง **DHT sensor library** (Adafruit) และ **Adafruit Unified Sensor**

ตั้งค่าในเมนู Tools ให้ตรงกับบอร์ด

| หัวข้อ | ค่า |
|---|---|
| Board | **ESP32 Dev Module** |
| Flash Size | **4MB (32Mb)** |
| Upload Speed | 921600 — **ถ้าอัปโหลดไม่ผ่าน ลดเป็น 115200** (ชิป CH340 บางตัวไม่ทนความเร็วสูง) |
| Port | พอร์ตที่โผล่มาตอนเสียบบอร์ด |

**ขั้นที่ 3 — อัปโหลด**

3. เปิดหน้าเว็บ `/dashboard/iot` กด "เพิ่มอุปกรณ์" → คัดลอก device key ที่แสดงขึ้นมา (แสดงครั้งเดียว)
4. คัดลอก `firmware/esp32-dht11/config.example.h` เป็น `config.h` แล้วกรอก Wi-Fi + device key
5. กดอัปโหลด
6. เปิด Serial Monitor ที่ 115200 ดูว่าอ่านค่าและส่งสำเร็จ

บอร์ดส่วนใหญ่มีวงจร auto-reset จึงเข้าโหมดอัปโหลดเองโดยไม่ต้องกดปุ่ม
ถ้าค้างอยู่ที่ `Connecting......___` ให้กดปุ่ม **BOOT** ค้างไว้ตอนที่ข้อความนั้นขึ้น แล้วปล่อยเมื่อเริ่มอัปโหลด

`config.h` ถูก `.gitignore` ไว้แล้ว รหัส Wi-Fi และ device key จะไม่ถูก commit ขึ้น repo

## 12. ปริมาณข้อมูลและขีดจำกัด

ที่รอบ 60 วินาที ต่ออุปกรณ์หนึ่งตัว

| ช่วงเวลา | จำนวนแถว | ขนาดโดยประมาณ |
|---|---|---|
| 1 วัน | 1,440 | ~0.15 MB |
| 1 เดือน | ~43,000 | ~4.5 MB |
| 1 ปี | ~526,000 | ~55 MB |

Supabase free tier ให้พื้นที่ 500 MB — รองรับได้หลายอุปกรณ์หลายปี
มีฟังก์ชัน `iot_purge_old_readings(keep_days)` ไว้ล้างข้อมูลเก่าเมื่อต้องการ
ตั้งให้ทำอัตโนมัติด้วย pg_cron ได้:

```sql
select cron.schedule('iot-purge', '0 3 * * *', $$select public.iot_purge_old_readings(90)$$);
```

**ข้อควรรู้:** โปรเจกต์ Supabase แบบฟรีจะถูกพักอัตโนมัติเมื่อไม่มีการใช้งานราวหนึ่งสัปดาห์
ถ้ามีอุปกรณ์ส่งข้อมูลเข้ามาทุกนาที โปรเจกต์จะไม่ถูกพัก แต่ถ้าถอดอุปกรณ์ทิ้งไว้ช่วงปิดเทอม
อาจต้องเข้าไปกด Restore ก่อนใช้งานอีกครั้ง

## 13. ความปลอดภัย

| ประเด็น | วิธีรับมือ |
|---|---|
| คีย์อุปกรณ์รั่วจากฐานข้อมูล | เก็บเฉพาะ SHA-256 ไม่เก็บคีย์จริง |
| ถอดบอร์ดไปอ่านคีย์ | คีย์ใช้ได้แค่ "ส่งข้อมูลของเครื่องตัวเอง" อ่านข้อมูลเครื่องอื่นหรือแก้เกณฑ์ไม่ได้ ถ้าบอร์ดหายให้กดออกคีย์ใหม่ |
| ปลอมข้อมูลส่งเข้าระบบ | ต้องมีคีย์ที่ถูกต้อง + ค่าที่เกินพิสัยเซนเซอร์ถูกตัดทิ้ง |
| ดักข้อมูลกลางทาง | ส่งผ่าน HTTPS และตรวจใบรับรองรากได้เมื่อตั้ง `ROOT_CA_PEM` |
| Webhook ปลอมจาก LINE | ตรวจลายเซ็น HMAC-SHA256 ด้วย channel secret ทุกคำขอ |
| นักเรียนเห็น LINE userId ของครู | RLS ปิดตาราง `iot_line_recipients` ไว้เฉพาะครู |
| endpoint cron ถูกยิงมั่ว | ต้องมี `Authorization: Bearer <CRON_SECRET>` |

**เรื่องที่ยังต้องระวัง:** `ROOT_CA_PEM` ที่เว้นว่างไว้จะทำให้บอร์ดข้ามการตรวจใบรับรอง
ข้อมูลยังถูกเข้ารหัสอยู่ แต่มีโอกาสถูกปลอมเป็นเซิร์ฟเวอร์ปลายทางได้
ควรใส่ใบรับรองจริงก่อนติดตั้งใช้งานถาวร (ดูวิธีดึงใบรับรองใน `firmware/esp32-dht11/README.md`)

## 14. การทดสอบ

ทดสอบได้โดยไม่ต้องมีบอร์ด — สร้างอุปกรณ์ในหน้าเว็บ แล้วยิงข้อมูลปลอมด้วย curl

```bash
# ส่งค่าปกติ
curl -X POST https://krukhayan-physics.vercel.app/api/iot/ingest \
  -H "Content-Type: application/json" \
  -H "x-device-key: kkp_xxxxxxxxxxxx" \
  -d '{"temperature_c": 26.5, "humidity_pct": 55}'

# ส่งค่าที่เกินเกณฑ์ สองครั้งติดกันเพื่อให้เข้าเงื่อนไข consecutive_required
curl ... -d '{"temperature_c": 35.0, "humidity_pct": 55}'
curl ... -d '{"temperature_c": 35.2, "humidity_pct": 55}'   # ครั้งนี้ควรได้ LINE

# ตรวจอุปกรณ์ออฟไลน์
curl https://krukhayan-physics.vercel.app/api/iot/cron/offline-check \
  -H "Authorization: Bearer <CRON_SECRET>"
```

## 15. แก้ปัญหาที่พบบ่อย

| อาการ | สาเหตุที่พบบ่อย |
|---|---|
| คอมไม่เห็นพอร์ตตอนเสียบบอร์ด | ยังไม่ได้ลงไดรเวอร์ USB (ดูหัวข้อ 11.4) หรือสายที่ใช้เป็นสายชาร์จที่ส่งข้อมูลไม่ได้ |
| บอร์ดรีสตาร์ทเองเป็นระยะ ขึ้น `Brownout detector was triggered` | อะแดปเตอร์จ่ายกระแสไม่พอตอน Wi-Fi ส่งสัญญาณ หรือสายยาวเส้นเล็กเกินไป — เปลี่ยนเป็น 1A ขึ้นไป |
| Wi-Fi อ่อนหรือหลุดบ่อยทั้งที่อยู่ใกล้เราเตอร์ | บอร์ดอยู่ในตู้เหล็กซึ่งบังสัญญาณ หรือใช้รุ่น 32UE โดยยังไม่ได้ต่อเสาอากาศ (ดูหัวข้อ 3.1) |
| อ่านค่าไม่ได้เลยตั้งแต่ครั้งแรก หลังเคยต่อ VCC เข้า 5V | GPIO อาจเสียหายถาวรจากไฟ 5V — ลองย้ายไปขา GPIO อื่นแล้วแก้ `DHT_PIN` ใน `config.h` |
| Serial ขึ้น "อ่านค่าจาก DHT ไม่ได้" | สายหลวม / ต่อ DATA ผิดขา / ใช้ตัวเปล่า 4 ขาแต่ไม่ได้ใส่ตัวต้านทาน 10 kΩ |
| ค่าแรกหลังบอร์ดบูตเป็น 0 °C / 0 %RH | เซนเซอร์ส่งเฟรมศูนย์ล้วนซึ่งมี checksum ถูกต้องพอดี ไลบรารีจึงรับมาเป็นค่าจริง — เฟิร์มแวร์และฝั่งเซิร์ฟเวอร์ดักทิ้งให้แล้ว ถ้ายังเจออยู่แปลว่าบอร์ดยังใช้เฟิร์มแวร์รุ่นเก่า ให้แฟลชใหม่ |
| ต่อ Wi-Fi ไม่ได้ทั้งที่รหัสถูก | ESP32 รองรับเฉพาะ **2.4 GHz** ต่อกับ SSID ย่าน 5 GHz ไม่ได้ |
| ส่งได้ 401 | device key ผิด หรือเพิ่งกดออกคีย์ใหม่แล้วยังไม่ได้แฟลชบอร์ด |
| อุณหภูมิสูงกว่าเทอร์โมมิเตอร์ 2–3 °C | เซนเซอร์อยู่ใกล้ตัวบอร์ดเกินไป ความร้อนจาก ESP32 รบกวน — แยกเซนเซอร์ออกมา |
| กราฟเป็นขั้นบันได | ปกติของ DHT11 ที่อ่านอุณหภูมิเป็นจำนวนเต็ม ถ้าต้องการเส้นละเอียดให้เปลี่ยนเป็น DHT22 |
| ไม่ได้รับ LINE ทั้งที่ค่าผิดเกณฑ์ | ยังไม่มีใครแอดบอท / ยังไม่ได้ตั้ง `LINE_CHANNEL_ACCESS_TOKEN` / ยังอยู่ในระยะพัก — ดูสาเหตุที่แท้จริงในแท็บ "ประวัติแจ้งเตือน" ซึ่งบันทึกข้อความผิดพลาดไว้ |
| หน้าเว็บขึ้นว่าออฟไลน์ทั้งที่บอร์ดทำงาน | นาฬิกาบอร์ดเพี้ยนเพราะ NTP ไม่ผ่าน หรือ `offline_after_s` สั้นกว่ารอบการส่ง |

## 16. ต่อยอดได้อีก

- **จอแสดงผลในห้อง** — หน้าเว็บโหมดเต็มจอสำหรับ TV หน้าห้องเซิร์ฟเวอร์
- **อัปเดตแบบเรียลไทม์** — ตอนนี้หน้าเว็บดึงข้อมูลใหม่ทุก 30 วินาที เปลี่ยนเป็น Supabase Realtime
  เพื่อให้ค่าขึ้นทันทีที่ข้อมูลเข้าได้
- **เพิ่มเซนเซอร์** — โครงสร้างตารางรองรับหลายอุปกรณ์อยู่แล้ว เพิ่มค่าที่วัดใหม่ (เช่น PM2.5, CO₂)
  ทำได้โดยเพิ่มคอลัมน์ใน `iot_readings` และเพิ่มค่าใน `metric` ของ `iot_alert_rules`
- **ใช้เป็นสื่อการสอน** — ข้อมูลจริงย้อนหลังใช้สอนเรื่องการถ่ายเทความร้อน ความชื้นสัมพัทธ์
  และการวิเคราะห์กราฟในวิชาฟิสิกส์ได้โดยตรง ดาวน์โหลดเป็นตารางจากปุ่ม "ดูเป็นตาราง" ในกราฟ
- **สำรองด้วยแบตเตอรี่** — ต่อ power bank คั่นไว้ ไฟดับแล้วบอร์ดยังส่งข้อมูลได้
  (และเป็นตัวบอกว่าไฟในห้องดับ ไม่ใช่บอร์ดเสีย)
